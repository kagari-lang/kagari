Suppose a running host must replace a rule without redirecting a call halfway
through it. Compile and prepare the replacement first, ask the runtime to publish
it, and keep using the same live Program handle for new work. Publication changes
the current code, not the identity or contents of every existing object.
Read <a href={page('host/overview')}>the first host</a> for artifact preparation and
<a href={page('host/ownership')}>scoped access</a> for host-state lifetimes.

## Replace one body through the SDK

The existing test
<a href={source('crates/kagari/src/runtime/tests/embedding/embedding_api.rs')}>`compiles_loads_executes_and_reloads_through_embedding_api`</a>
is a compact source reference, not a standalone tutorial executable. It compiles
two prepared programs with the same source name, `game/main.kgr`: first
`fn main() -> i32 { 1 }`, then `fn main() -> i32 { 2 }`. It loads the first as
`game.main` and calls `ProgramEntry::Main`, observing a rooted result of 1.

This exact **excerpt** begins after that initial load and call. `second` is the
already compiled replacement `PreparedProgram`; `runtime` and `loaded` are the
existing runtime and live Program handle. The test supplies imports and setup.

```rust
    let previous = runtime.runtime().select_program(&loaded).unwrap();
    runtime
        .reload_program(
            &loaded,
            &second,
            ReloadOptions {
                program_name: Some("game.main".to_owned()),
            },
        )
        .expect("compatible module should reload");
    let reloaded = runtime.runtime().select_program(&loaded).unwrap();
    assert_eq!(reloaded.id, previous.id);
    assert_eq!(reloaded.epoch.0, previous.epoch.0 + 1);
```

Calling `execute(&loaded, ProgramEntry::Main, &[], &context)` then returns 2.
The test inspects `report.return_value.value(runtime.runtime().gc())`; it does not
pretend the raw result owns its own lifetime. Ordinary reload itself calls neither
version's `main` and performs no hidden candidate initialization.

The current <a href={source('crates/kagari/src/runtime.rs')}>SDK declaration</a>,
shown as a **signature excerpt**, is:

```rust
    pub fn reload_program(
        &self,
        previous: &Program,
        program: &PreparedProgram,
        options: ReloadOptions,
    ) -> ReloadResult<()>
```

`ReloadOptions` contains `program_name: Option<String>` for the diagnostic label.
Supply the intended live Program, not an unrelated runtime's handle. Successful
reload advances that installation; it does not return a replacement handle.
Preparation has its own `ProgramPreparationError`; SDK reload errors use
`EmbeddingError`, including `ReloadValidation { code, message }`.

## Understand the publication boundary

The SDK first acquires the runtime's exclusive publication guard, stages the exact
prepared candidate and publishes it. Publication requires a host-top-level boundary
with no synchronous script, driver, callback or reentry scope; parked work may remain.
Staging checks
the candidate's module/schema and ABI contracts, public paths and signatures,
host registrations and typed-path fingerprints. It does not install an unchecked
body just because the source file has the same name.

Publication rechecks the expected base version and candidate references before
atomically making the generation current. A rejected candidate leaves the current
entry unchanged; dropping a staged candidate discards it. Atomicity is **per
runtime**, not a transaction across all your actors, persistent storage or services.
The host owns any coordination across runtimes.

For an observable rejection, the same test source contains
`reload_rejects_typed_path_fingerprint_changes_without_publishing_epoch`. It
changes the host path contract and expects `KG_RELOAD_PATH_FINGERPRINT_MISMATCH`,
then checks that both the loaded count and the current epoch are unchanged.
Treat this as a failed update, keep serving with the existing generation, and
report the structured code. Renaming/removing public paths or changing their
signatures is also incompatible, not an invitation to repair callers at runtime.

## Distinguish live bindings from retained computations

Existing live handles observe the current publication. The focused SDK test
<a href={source('crates/kagari/src/runtime/tests/embedding/scoped_calls.rs')}>`scoped_native_calls_accept_compatible_reloaded_descriptors`</a>
provides a second concrete scenario. Its `prepare(offset)` helper compiles public
`direct`, `native` and `heal` wrappers. The native wrapper adds the offset to a
registered read of host-owned `Stats.hp`. This exact **excerpt** shows the handoff:

```rust
    let context = ExecutionContext::default();
    let mut runtime = engine.runtime(context.clone());
    let old = runtime
        .load_program(&prepare(0), Default::default())
        .unwrap();
    let descriptor = runtime
        .runtime()
        .bind_rust_type::<Stats>(&old.root())
        .unwrap();
    runtime
        .reload_program(&old, &prepare(100), Default::default())
        .unwrap();
    let current = old.clone();
```

The surrounding test registers the type/functions explicitly. With hp starting
at 40, it calls through `old`, `current`, then `old` in a host scope. The native
wrapper returns 140, 141, then 142 because all three calls use current code adding
100, and each round also heals by one. Final host hp is 43. The rule changed without
copying or migrating that Rust object. Read the linked test for the checked scope.

Ordinary named `Function` bindings, direct calls, interface calls and native callback
calls select current implementations of their checked declarations. Created closures,
cold Futures and admitted frames/queued invocations instead retain their selected
bodies and matching type environments. A resumed old body still makes ordinary
inner calls to current helpers. Synchronous reentry preserves roots, scoped borrows
and cancellation; it does not establish an old dependency-version domain. Old exact
code becomes reclaimable when its remaining computation and metadata owners end.

## Keep static state and the original initializer recipe

Consider this **illustrative source scenario**. V2 changes only `version()` to
return 20; all direct initializer expressions and checked bindings stay unchanged.

```kagari
static var COUNT: i32 = 0;
static val CALLBACK: fn() -> i32 = || version() + COUNT;
static val LATE: i32 = version();
fn version() -> i32 { 10 }
```

Suppose V1 has initialized COUNT and CALLBACK, COUNT is now 2, and LATE is still
unread. After compatible V2 publication:

| Operation | Result under the publication contract |
| --- | --- |
| Increment COUNT | The same Ready cell changes from 2 to 3; publication did not reset it. |
| Invoke CALLBACK | The retained closure body calls current `version()`, returning 20 + 3 = 23. Retaining a closure body does not pin ordinary helper calls. |
| First read of LATE | The original V1 recipe calls current `version()` and initializes LATE to 20. |
| Inspect an already Failed static | It remains Failed; changing a helper does not retry initialization. |

Changing `COUNT`'s direct initializer from `0` to `100`, or retargeting LATE's
checked `version` binding through an alias, is rejected even if the cell is already
Ready. Comments and whitespace may change. Ordinary called helper bodies may change;
there is no transitive protection or global `Unknown` freeze. A fresh independent
installation gets fresh cells. Loading, inspection and publication force no initializer.

Staging shares existing cells and keeps additions private until publication.
A stale, invalid or abandoned candidate cannot change existing cells or active
bindings. You may add statics in an existing module, but cannot delete, rename,
move, or change the declared type, mutability or visibility of an existing static,
including a private one. Relevant recursive applied schemas remain checked even
when a cell holds None or an empty collection. Other checked additions follow the
<a href={source('docs/spec/module-activation.md#compatible-declaration-changes')}>declaration compatibility rules</a>;
existing signatures, layouts and trait relationships still cannot change.

Publishing older code is not state rollback: it cannot remove a static added
since that version, restore old values or retry a Failed initializer. See
<a href={source('docs/spec/module-activation.md#static-publication-compatibility')}>static publication compatibility</a>
and <a href={source('docs/spec/runtime.md#persistent-static-cells')}>cell ownership and GC</a>.

Hash/Eq bodies and their ordinary helpers support normal hot updates. A retained
HashMap/HashSet keeps its checked key relationships, but lookup, insertion and
removal call current implementations. Host `ScriptMap`/`ScriptSet` handles select
current callback bodies on each lookup, just like script operations. Publication
neither rehashes tables nor pins old protocols. If an update changes a stored key's
hash or equality, later lookup may fail: preserving stable key semantics is the
user's responsibility, not a guarantee of compatible publication. Engine memory,
GC/rooting, scoped-borrow, reentry and cancellation safety remain enforced.
The <a href={source('docs/spec/collection-access.md#stored-key-protocols-across-reload')}>collection protocol contract</a>
explains membership versus caller-selected content operations.

## Do not confuse retention with state migration

Compatible reload does **not** migrate object layouts, replace durable application
state, extend a host scope, or make a taken opaque payload available again. Old
receiver and field descriptors cannot silently switch to a new Rust layout.
A retained generation preserves code dependencies, not expired host access.
Static persistence does not automatically include cells in a disk snapshot or
provide a state-migration protocol. Kagari provides ordinary host value access and
conversion; applications own persistence and data transformations. Durably storable
does not mean serializable.

Static initializers are synchronous: they cannot create a cold Future, spawn,
create an async scope or await, even through native reentry. During ordinary
execution, Future/Task values can be stored under the existing durable-storage
and scope rules, for example in an initialized Option. Storage does not extend
their scopes, revive them or change their pinned bodies/providers. Native static
execution is unsupported; interpreter fallback must be selected before native
entry, not after effects. See
<a href={source('docs/spec/module-activation.md#async-activation')}>async activation</a>
and <a href={source('docs/spec/bytecode.md#persistent-static-descriptors-and-transitions')}>backend limits</a>.

Lower-level runtime APIs also permit an explicit restricted candidate session.
Such a session may compute and mutate candidate-owned nonstatic objects, but
cannot perform external modifications or access any static cell, even a Ready
cell or one introduced by the candidate. Indirect calls and host reentry do not
bypass that restriction. Publication follows session completion and revalidation;
ordinary `reload_program` does not opt into that session for you. Reload does not
migrate business state or suspended executions. The
<a href={source('docs/spec/module-activation.md')}>activation contract</a> owns these
rules. For current deployment/backend limits, continue to
<a href={page('reference/status')}>status and limits</a>.
