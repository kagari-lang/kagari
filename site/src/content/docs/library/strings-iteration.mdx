## Format a message

Ordinary strings interpolate names without an `f` prefix. Bind computed values
before using them in a hole:

```kgr
val name = "Kagari";
val score = 40 + 2;
val message = "Hello {name}, score={score}";
val diagnostic = "name={name:?}";
```

`message` is `"Hello Kagari, score=42"`. A hole must be exactly `{name}` or
`{name:?}`, with no internal whitespace. Fields, calls, arithmetic and paths such
as `{player.name}`, `{compute()}` and `{module::VALUE}` are rejected; bind their
results first. Names use normal resolution, including parameters, constants,
accessible statics and imported aliases. Ordinary holes require `Display`, while
`:?` requires `Debug`: the debug representation of `name` includes quotes.
Doubled braces, `{{` and `}}`, produce literal braces.

Each occurrence reads its name and formats it before reading the next name.
Repeated names are not captured once at string entry. For example, in
`"{first}{STATE}"`, `first`'s formatter may update STATE, and the next hole observes
that update. Reading a static may initialize it. A trap skips later holes without
undoing completed effects.

When replacing an old expression hole, do not eagerly compute every argument if
formatting has effects. Keep the original ordering with an intermediate string:

```kgr
val first = make_first();
val rendered = "{first}";
val second = make_second();
val message = "{rendered}: {second:?}";
```

This formats `first` before calling `make_second()`. Keep such bindings inside
their original branch or argument-evaluation position.

A `String` is an immutable value. Trimming, replacement and slicing produce
strings rather than exposing a writable character buffer or a borrowed Rust
`&str`. Assigning a string does not grant mutation of its contents.

## Write literal text and multiple lines

Raw strings do not interpret escapes or interpolation. Use `r"..."` when the text
has no quotes, or add matching hashes around the quotes for JSON and templates:

```kgr
val path = r"C:\games\Kagari";
val template = r#"{"message":"Hello {name}","newline":"\n"}"#;
val braces = "Literal {{name}}";
```

Here `{name}` and `\n` remain literal text inside `template`. Raw delimiters allow
zero through 255 hashes. Cooked strings support `\n`, `\r`, `\t`, `\0`, quote and
backslash escapes, ASCII `\xNN` and Unicode `\u{...}` escapes; for example,
`"\u{1F_600_}"` produces 😀. A brace produced by `\u{7B}` does not start a hole.

Both cooked and raw strings can span source lines. They retain indentation and
initial/final newlines, with CRLF normalized to LF and no automatic dedent:

```kgr
val text = "first
  second";
val joined = "left\
    right";
```

`text` contains `"first\n  second"`. In a cooked string, a backslash immediately
before a physical line break removes that break and following ASCII whitespace,
so `joined` is `"leftright"`. Raw strings retain the backslash and line break;
a `\n` escape in a cooked string inserts a newline rather than continuing a line.
See the <a href={source('docs/spec/syntax.md#string-literals')}>literal contract</a>
for delimiter, escape and literal-only-context rules.

## Construct mutable byte arrays

Use `b'A'` for a single `u8` rather than a Unicode `char`. Cooked `b"..."` and raw
`br"..."` / `br#"..."#` literals produce fixed-length `[u8]` arrays, not strings:

```kgr
fn packet() -> [u8] { b"AB\0\xFF" }
val first = packet();
val alias = first;
val second = packet();
alias[0] = b'Z';
```

`first` and `alias` now contain Z, B, NUL and FF; `second` still contains A, B,
NUL and FF. Each evaluation of a byte-string literal creates fresh storage, even
for `b""` or `br""`. Copying or returning an existing array shares that array
instead. Compare contents with `==` and storage identity with `===`: separately
evaluated empty byte arrays have equal contents but different identities.
Elements can be replaced, but the array cannot grow. Builtin array iteration
awaits a collection cursor provider.

Direct byte-literal text must be ASCII. Cooked forms accept quote/backslash
escapes, `\n`, `\r`, `\t`, `\0` and `\x00` through `\xFF`, but no `\u{...}`
escapes. `b"中文"` is rejected instead of silently UTF-8-encoding the text. A
payload such as `b"\0\xFF"` needs no UTF-8 validity check.

```kgr
val escaped = b"\xFF";
val literal = br"\xFF";
val template = br#"{"name":"{name}"}"#;
val braces = b"{name}{{}}";
```

`escaped` contains one byte, FF; `literal` contains four ASCII bytes: backslash,
x, F, F. Neither cooked nor raw byte strings interpolate or collapse doubled
braces, so `template` and `braces` need no `name` binding. Raw delimiters use the
same zero-to-255 matching hashes as raw text strings; the prefix is `br`, not `rb`.
Both forms retain multiline indentation and normalize source CRLF to LF. Cooked
backslash-line-break continuations remove the break and following ASCII whitespace;
raw forms retain the backslash and line break. Standalone CR is rejected outside
continuation whitespace.

These literals do not add String indexing or implicit text conversion.
See the <a href={source('docs/spec/syntax.md#byte-literals')}>byte literal contract</a>
for the exact lexical and typing rules.

## Work with UTF-8 bytes deliberately

The `String` type comes from core; the methods in this section require the
explicitly installed `std::string` provider. `len()` returns a `u64` count of **UTF-8 bytes**, not displayed characters or Unicode scalar values.
For example, `"é!"` has three bytes: two for `é`, then one for `!`.
`slice(0, 2)` selects `é` using a half-open range; `slice(0, 1)` traps because its
end splits a UTF-8 encoding. Reversed or out-of-range slices also trap with
`IndexOutOfBounds`. A checked slice returns a string value, not a script borrow
whose lifetime must be tied to the original string.

For searching, `find(pattern)` returns `Option<u64>` containing a **byte**
offset. `contains`, `starts_with`, `ends_with` and `replace` use literal patterns,
not regular expressions. `trim` and its one-sided variants remove Unicode
whitespace. The current provider has no `split`, `chars`, `char_indices` or
`bytes` method, and String itself does not implement `Iterable`.

Empty patterns have defined behavior: `find("")` returns `Some(0)`, while empty-pattern
replacement uses Unicode scalar boundaries, including both ends.
String indexing, regex and locale APIs are not provided. The
<a href={source('docs/spec/builtins.md#primitive-operations-and-formatting')}>string contract</a>
and <a href={source('crates/kagari-stdlib/src/foundation/string.rs')}>String declarations</a>
own the exact supported surface.


## Delay work until consumption

The <a href={source('crates/kagari/tests/fixtures/embedding/installation/bag.kgr')}>script collection</a>
supplies a cursor for its items. In its
<a href={source('crates/kagari/tests/fixtures/embedding/installation/bag-consumer.kgr')}>consumer</a>,
`bag` holds `2` and `5`. `bag.iter().map(|x| x * 2)` builds an adapter without
pulling an item. `mapped.next()` then returns `Some(4)`. A `for` loop over that
same cursor sees only `10`: it does not start again at `4`. Neither module needs stdlib.

Transformations such as `map`, `filter` and `take` are lazy. Terminal operations
such as `collect`, `fold`, `sum` and `count` consume items. For `collect`, `sum`
and `product`, a destination type annotation or explicit method type argument
must determine the result type. `find`, `any` and `all` can stop early, without
an extra pull after the answer is known.

`take` and `skip` accept `u64` logical counts; `count()` returns `u64`, and
`enumerate()` pairs each item with a `u64` index. Counts remain wide even when the
host has narrower addresses. Taking a large prefix of a short iterator does not
allocate a buffer of that size; collection and allocation remain separate steps.

These are ordinary `Iterator` methods. A container that implements `Iterable`
starts the chain with `values.iter().map(f)`; a cursor calls `map(f)` directly.
Calling `iter()` on a cursor returns the same iterator at its current position.

## Implement ordinary iteration

Implement `Iterable::iter` on your collection to supply a cursor; its `Item`
must agree with the collection's `Item`. Implement `Iterator::next` on the
cursor to return `Some(item)` or `None`. Implement `FromIterator` on a
destination to let callers collect into it, as the script collection does.

A `for` loop evaluates its source once, calls `iter` once, then calls `next`
until `None`. `continue` asks for the next item; `break` stops without another
read. This is method dispatch with normal side effects, not a Rust borrow or
move of each stored object.

## Understand saved progress and mutation

Aliases of the **same cursor or adapter** share progress. Calling `iter()` on a
collection can create a fresh traversal. A callback failure does not rewind an
item already pulled. Core adapters do not reject a nested `next` just because
it is nested; ordinary traps, cancellation and call-depth limits still apply.

In the deferred native collection design, retaining a cursor does not lock its
collection against writes. Replacing
a sequence element can be seen by the next read, but growth, removal or reordering
changes the structure. Such an edit commits through any writable alias, and the
existing cursor traps on its next source read. A read-only view does not prevent
that invalidation. Already completed writes and callback effects remain visible.
A lazy adapter checks only sources it actually pulls; `take(0)`, for example,
does not advance its source to discover an otherwise stale cursor.

Custom iterators own their own state and consistency rules. Do not assume every
iterator resets, is fused after `None`, reports an exact length or can be cloned
into independent progress. See the external
<a href={source('docs/spec/builtins.md#iteration-protocols')}>iteration contract</a>
for all current adapters and consumption rules, and
<a href={source('docs/spec/collection-access.md')}>collection access</a> for mutation
boundaries. Continue to <a href={page('reference/specifications')}>the reference index</a>
when you need a precise rule rather than a walkthrough.
